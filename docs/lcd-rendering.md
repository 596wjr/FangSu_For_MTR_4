# MTR4 LCD 独立绘制

2026-10-29：替代向 JCM 私有表注入 `fangsu_lcd` 转发脚本的实现。重构前备份提交为 `1501bd0`。

资源包仍使用 `lcd.id / slots / script / extraConfig`。Java 的 `LcdManager.injectLcd`、`LcdBase.draw` 和 JS 的 `draw(g, state, trainStatus, info, extraConfig)` 保持不变。

## 链路

1. 方速 `initResources` 暂停 LCD 提交，刷新 ResourceUtil 与已有脚本 holder。
2. 全部资源初始化完成后发出 LCD 重载信号，由客户端线程清理旧实例并加载 `LcdVehicleRegistry`。
3. MTR `RenderVehicles.render` 帧头推进状态帧号；在 MTR `VehicleResource.queue` 收尾，将当前车厢的 `StoredMatrixTransformations` 交给方速。
4. 方速按车辆运行时 ID、该车厢的车型 ID 创建 LCD。每列车中的同车型车厢共享纹理与状态，不同车型分开。
5. 后台绘图线程最多每 50ms 提交一次重绘；同一 LCD 始终最多一个任务。Future 完成后客户端线程上传完整图像，再提交模型。
6. 模型使用 MTR RawMesh/OptimizedModel 和 MTR 模型队列。保留原 JCM 的局部 `(0,-1,0)` 原点偏移、slots 顶点的 Y/Z 换向和 UV 约定。

不再注册 JCM 脚本、修改车辆 scriptId 或向 JCM 脚本作用域注入对象。JCM 仅保留车辆状态、站序请求以及现有站序数据适配。

## 资源所有权

模型上传直接使用 MTR 4.0.5 发布包已有的 `GlStateTracker.capture/restore`，并通过访问器读取保护标记：只有本层捕获时才负责恢复，避免提前结束外层保护。旧版 restore 强制改变的剔除和深度写入状态也会恢复到调用前。每块 LCD 无需调用全局 `beginReload/finishReload` 重载着色器。方速保存并释放 VAO、VBO、IBO 和动态纹理。绘图线程只写堆内 BufferedImage，不能操作已经释放的 NativeImage。

MTR 的正常同步会替换 `VehicleExtension`，同时沿用该车辆的 `persistentVehicleData`。LCD 按车辆 ID 和这份持久运行数据识别实例，只更新车辆快照引用，保留模型、纹理、绘图任务和 state。资源重载、车辆消失、持久运行数据更换、编组移除某车型和切换世界才会清理相应实例。创建日志包含运行时车辆 ID，便于区分两列同型号的车。绘图失败时保留最后一次成功上传的内容，5 秒后重试。配置解析失败只禁用该车型，F3+T 后允许重新创建。

线路状态直接采用站序响应里的 `SimplifiedRoute`，保留其车站详情；按 ID 查询时也回退读取 JCM 的公开数据缓存。普通线路可能存在于 JCM 独立缓存而未进入 MTR 当前附近的数据表，不能因第二次查表未命中而丢掉已经获取的线路。

客户端初始化显式注册补充线路 S2C 接收器。LCD 在站序已到但线路详情缺失时，按 thisRouteId/nextRouteId 主动补取详情，同线路最多每 5 秒请求一次；该链路不依赖 JCM 脚本或绘制回调。通道沿用 hidden_routes_* 历史包名，但明确按 ID 请求时也返回普通线路，空请求仍只取全部隐藏线路。有效线路 ID 可以是负数，仅 0 表示无线路。响应同时写入方速补充缓存和 JCM 的公开数据缓存，并清掉旧线路图缓存；联机时客户端、服务端都需包含这次通道修复。

尚未同步完整时不缓存空线路图，后续数据到达后继续重试。持续缺失超过 5 秒时每辆车只记录一次诊断，包含线路 ID、站序数量与数据获取状态。

## 开门方向（两版同步）

实时观测绑定站台和反向状态，关门或换站后失效；缓存只匹配同车型、同编组和总长差不超过 2 米的记录。`predictedDoorOpenSides` 保留非反向规范帧的原有含义；`getDoorOpenSide(carIndex)` 统一执行实时优先、预测左右换算，未知保持 UNKNOWN。MTR4 不再把车辆级门开度直接当成左右两侧同时开门。

进站前，按真实行驶路径寻找前方有停站时间、且不是车辆段的下一站。该站该配置方向仍为 UNKNOWN 时，MTR4 创建不注册到运行世界的只读 Vehicle，以站台末端里程复用 MTR 转向架/车体姿态解算；MTR3 用原里程表、车型纵向偏移和正反向车节顺序计算停放位置。计算不改写真实列车里程、平滑数据或门状态。

逐车厢扫描原版站台、原版 PSD/APG 和方速屏蔽门，方速锁定门与原版门的 UNLOCKED 状态参与判定。预测只读方块，不调用会联动屏蔽门的方法，不提前开门。目标区块/模型未加载时保留 UNKNOWN，每 10 tick 重试；已知方向不重复扫描。预测只保存在本地内存，F3+T/换世界后清理，不上报成实际观测。

开始实际开门后立即用本站实时方向覆盖预测（MTR3 汇齐本列逐节观测，MTR4 门开度超过 0.05 即采集），再沿原缓存协议同步实际记录。稳定的 NONE 也会回写，避免错误预测在关门后重新出现。站台 ID 允许负数，仅 0 表示无站台；协议字段与 Java/JS 调用不变。

MTR3 备份为 `17ba3ab`。MTR3 保留原有渲染提交链路，仅同步门侧修复、LCD 脚本状态隔离及资源重载后的状态刷新。

## 手动验证

- 原 Java LCD 和 `lcd.script` 资源包均无需改配置；确认左右屏位置、UV、自发光和车体一致。
- 混编不同 LCD 车型，另放两列同型号但线路不同的车，检查纹理和状态互不串用。
- 乘车/下车、倒车、坡道、摇晃和超高轨道，检查 LCD 与车体同步。
- 同一列车先后停靠左右侧站台；首次停靠无缓存时，在目标区块已加载后应于开门前得到停车预测，实际开门后以本站观测校正。
- 仅放原版 PSD/APG、仅放方速屏蔽门，以及锁定门、部分车厢不贴站台的情况；预测时屏蔽门不能提前打开。
- 目标区块尚未加载时保持 UNKNOWN，加载后重试；换站或关门后不沿用上一站实时方向。
- 反向运行仅翻转预测一次；异车型或异编组缓存不参与预测；NONE 不当成 UNKNOWN。
- 修改 JS 常量后 F3+T，检查已有屏幕更新；同时修改 slots、extraConfig，确认 MTR4 重建模型与绘制状态。
- 绘制脚本报错后修复并 F3+T，检查失败冷却和已耗尽重试的绘制项恢复。
- 连续 F3+T、移除车辆、退出并重新进入世界，检查旧动态纹理和网格释放。

按仓库约定未执行编译或游戏验证；上述项目需手动实测。
